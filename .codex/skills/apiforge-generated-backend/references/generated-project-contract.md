# Current generated-project contract

V1 target preflight checks source/composed identifier lengths, single VARCHAR
capacities and individual/composite STRING index bytes under MySQL >=8.0.16,
utf8mb4, InnoDB DYNAMIC/16 KiB. Strict mode with NO_BACKSLASH_ESCAPES disabled is
required for import/runtime; database defaults are caller-configured. Whole-row
layout and scalar storage limits remain DB-authoritative. STRING/ENUM literals
share escaping. Generated Node engines require >=18. G19 disk publication uses
sibling staging and reversible user-root moves as described below.

This reference describes current implementation behavior. It is not a promise that missing standalone-project features already exist.

## Generation modes and file set

`src/codegen/codegen.js` consumes validated optimized IR. `generate(ir, true)` writes under repository `output/`; `generate(ir, false)` returns the same `{ path, content }` entries without writing. The compiler API uses the in-memory form.

Current generation returns seven fixed files plus three files per entity:

```text
database/schema.sql
config/db.js
.env.example
package.json
README.md
models/<Entity>.js
controllers/<entity>Controller.js
routes/<entity>Routes.js
server.js
swagger.json
```

- `database/schema.sql`: MySQL entity tables followed by relationship DDL.
- `config/db.js`: `mysql2/promise` pool configuration.
- `.env.example`: environment-variable template.
- `package.json`: generated-project metadata, `npm start`, and the required runtime dependencies using APIForge-compatible version ranges.
- `README.md`: concise install, environment, MySQL schema-import, startup, route, and OpenAPI-location instructions.
- `models/`: parameterized CRUD queries and source-side relationship query helpers.
- `controllers/`: CRUD handlers, typed write validation and field authority, relationship handlers, and JSON responses.
- `routes/`: per-entity CRUD and source-side relationship routes.
- `server.js`: dotenv loading, JSON middleware, route mounts, `/health`, global error handler, and startup.
- `swagger.json`: OpenAPI 3.0.0 paths and component schemas.

Disk generation uses `src/codegen/publish-output.js` to write and verify the complete new file collection in a unique sibling staging directory before touching published output. After renaming existing output to `backup/previous`, it moves each user-owned root entry, including `.env` and dependency trees, to staging with one same-filesystem rename. The generator-owned `models/`, `controllers/`, `routes/`, `config/`, and `database/` directories and generated root files are excluded. User entries are opaque filesystem objects: no recursive copy, traversal, link cloning, or `node_modules` special case is used. Replacement removes obsolete managed files while preserving user-owned root objects and files outside `output/`. Invalid IR and content-generation failures still occur before disk publication.

Renaming staging to `output/` after all user roots move is the commit point. Transfer or publication failure reverses transferred user-root moves before restoring the previous output. If a user-root rollback fails, both recovery trees are retained, incomplete old output is not published, and exact surviving/restore paths are reported with the original error. Cleanup errors never replace an earlier failure. After successful publication, backup cleanup failure leaves the valid new output published and throws the cleanup I/O error with `outputPublication.published = true`; CLI exit status remains 1 and includes runtime context alongside its existing codegen failure diagnostic. No new compiler diagnostic code or API response field is introduced. This covers handled failures in one operation, not concurrent publication or process/OS crash recovery. See `docs/atomic-output-publication-verification.md` for platform evidence and regression coverage.

## Dependencies and environment

For programs with DATE/TIMESTAMP fields, db.js configures mysql2 timezone Z and
dateStrings for those two types. Each checked-out promise connection awaits
SET SESSION time_zone='+00:00' before application query/execute; failed setup
destroys the connection. This is repeated on reuse. Application-query failures
also destroy the lease before propagating unchanged errors through G06.
TIMESTAMP schema imports set UTC and explicit_defaults_for_timestamp=ON before
DDL, preventing both shifted static defaults and legacy implicit auto attributes.
Declared DATE reads retain YYYY-MM-DD; TIMESTAMP SQL strings normalize to T/Z
on CRUD and all related-target reads; null stays null. Model writes validate
and convert only a private copy; canonical create echoes and omitted arbitrary
defaults retain the existing response contract. Filters share strict validation
and bind TIMESTAMP as UTC SQL text; trusted sorting is unchanged. OpenAPI uses
date/date-time plus strict canonical patterns/descriptions and public defaults.
Non-temporal projects retain their previous generated bytes. No files or runtime
dependencies are added. See docs/date-timestamp-verification.md.

Generated runtime code requires:

- `express`
- `dotenv`
- `mysql2` through `mysql2/promise`

The generated `package.json` declares only `express`, `dotenv`, and `mysql2`, using the version ranges from APIForge's own dependency manifest, and defines `npm start` as `node server.js`. No lockfile, database bootstrap, or `.env` is emitted. `.env.example` contains `PORT`, `DB_HOST`, `DB_USER`, `DB_PASSWORD`, and `DB_NAME`, with code fallbacks for local MySQL and database `apiforge_db`.

The generated README documents dependency installation, `.env` creation, MySQL database and schema preparation, startup, mounted route prefixes, and the root-level `swagger.json`. The generated server does not automate database creation or schema import.

## SQL contract

G16 target preflight models physical entity/junction columns and indexes without
changing SQL bytes or public IR. SEM037 covers 1017 columns, 64 secondary indexes,
the stricter stock-MySQL 64-total-index cap including PRIMARY, 16 key parts,
3072-byte full keys, logical/DYNAMIC admission row budgets, ENUM definition limits,
internal InnoDB column names and out-of-storage-range numeric DEFAULT literals.
Supporting FK indexes reuse an existing leftmost prefix; ONE_TO_ONE reuses its
UNIQUE and M2M adds only the target-side supporting index. Deployment defaults must
meet the documented target; the compiler does not inspect running server settings.
See docs/mysql-target-preflight-completion-verification.md for live evidence and
the conservative 16 KiB local-record model. HTTP numeric semantics are unchanged.

UUID fields and keys map to CHAR(36) CHARACTER SET ascii COLLATE ascii_bin; all
referencing/junction columns use identical physical types and collations.
getEffectiveKey distinguishes generation auto_increment/runtime_uuid/none;
autoGenerated remains a compatibility flag for either generation mode. UUID
without a PK never generates. A no-DEFAULT UUID PK uses Node core crypto.randomUUID
once per omitted/optional-null create. REQUIRED null rejects; omission generates.
Supplied keys win, static DEFAULT keys never generate, and input objects are
copied privately. UUID emits neither AUTO_INCREMENT nor runtime SQL DEFAULT.

UUID body and equality-filter validation shares the semantic/IR pure validator;
UUID item/source/target association path keys return 400 before model/DB calls.
PUT key immutability is unchanged. All CRUD/target reads validate UUID fields and
UUID FK columns; malformed external DB values fail sanitized 500, optional null
remains null and STRING remains untouched. OpenAPI string/uuid includes the exact
lowercase pattern across operation roles, filters, paths, FKs and association
echoes. Runtime UUID Create keys are optional; Read/CreateResult keys nonnullable.
UUID-only generation does not enable temporal pool configuration. No runtime
dependency/file is added, and non-UUID generated samples remain byte-compatible.

- Types map as `INT -> INT`, `STRING -> VARCHAR(255)` by default, `FLOAT -> FLOAT`, and `BOOLEAN -> BOOLEAN`. A STRING length bound above 255 widens the generated `VARCHAR` capacity to that bound; relationship foreign-key types use the same resolution when the primary key is a STRING.
- An explicit `INT` primary key without a default is auto-incremented. A primary key with a default omits auto-increment. If no primary key is declared, SQL prepends `id INT PRIMARY KEY AUTO_INCREMENT`.
- `REQUIRED`, `UNIQUE`, typed defaults, numeric `MIN`/`MAX`, and STRING `MIN_LENGTH`/`MAX_LENGTH` become `NOT NULL`, `UNIQUE`, `DEFAULT`, and `CHECK` clauses as applicable. STRING-length checks use `CHAR_LENGTH`.
- String defaults escape single quotes by doubling them. MySQL reserved or otherwise unsafe identifiers are backtick-quoted by the general identifier helper.
- Entity tables are emitted before relationship DDL.
- ENUM fields map to native `ENUM(...) CHARACTER SET utf8mb4 COLLATE utf8mb4_bin`.
  ENUM literals reuse SQL formatting with backslash escaping enabled; old STRING
  formatting remains byte-compatible. The schema assumes MySQL's normal
  backslash-escaping mode. Native ENUM trims trailing declaration spaces.

Relationship SQL:

| Cardinality | Current storage |
|---|---|
| `MANY_TO_MANY` | `<Source>_<Target>` junction table, composite key, two cascading foreign keys. |
| `ONE_TO_MANY` | Nullable source foreign-key column on the target table with `ON DELETE SET NULL`. |
| `MANY_TO_ONE` | Nullable target foreign-key column on the source table with `ON DELETE SET NULL`. |
| `ONE_TO_ONE` | Unique source foreign-key column on the target table with `ON DELETE CASCADE`. |

## Express and route contract

Explicit auto-generated INT create keys supplied as null or numeric zero resolve
from the actual ResultSetHeader.insertId. A generated 42 returns 42; a zero header
preserves stored zero under NO_AUTO_VALUE_ON_ZERO. Supplied nonzero keys retain
precedence; omitted auto keys, defaulted keys, optional-null validation and PUT
immutability are unchanged. CreateResult marks explicit auto keys nonnullable,
while Create still accepts optional null input.

For source-declared explicit auto INT keys, POST rejects negative integers with
400 before model/DB access; ordinary INT and INT DEFAULT keys are unaffected.
Create/CreateResult/Read use minimum0 for this key. MIN/MAX on a no-DEFAULT INT
PK fails SEM037 at the first bound before IR/codegen because MySQL CHECK cannot
reference AUTO_INCREMENT. Do not silently drop bounds or change the resolver's
NULL/zero behavior. Direct model general validation architecture is unchanged.

- Models use promise-based MySQL queries with value placeholders and `INSERT/UPDATE ... SET ?` payload binding. Empty valid creates use `INSERT ... () VALUES ()` for database-supplied values.
- A shared codegen effective key selects the explicit PRIMARY KEY or implicit integer id for SQL, item predicates, relationships, collections and OpenAPI. Create resolves a supplied explicit key first, otherwise generated insertId, otherwise typed declared key DEFAULT; unresolved non-generated omissions remain database-authoritative. Responses copy submitted data then safely define the resolved own key, without reloading arbitrary defaults or mutating input. Caller-supplied implicit id is rejected by POST/PUT before model access; explicit INT/STRING keys remain accepted on POST.
- PUT takes identity from URL :id and rejects any explicit own PK property with 400 `Field '<key>' is immutable.`, even the same value/null. Order: shape, unknown own keys, immutable PK, then declaration-order field checks. A shared generated policy/metadata also guards direct model updates before SQL, including implicit effective-key own properties. Non-key updates still use the original key in UPDATE/reread; empty PUT only rereads. WRITE_FIELDS remains the create-authorized declared set; PRIMARY_KEY carries origin, generation and typed default metadata and narrows the update policy, without introducing synthetic writable fields.
- Model fields remain source-declared; query/read metadata includes implicit id. OpenAPI marks it integer/readOnly and does not require it in requests. No-PK declared id in any casing fails semantic SEM033 before generation; explicit keys permit ordinary id-like fields. AST/source symbols/IR/optimized IR do not gain synthetic fields.
- Controllers return `201` for create, `200` for successful reads/updates/deletes, `404` for missing CRUD or singular related records, and `400` for generated validation failures. The G06 taxonomy returns sanitized `409` for recognized write/delete DB conflicts, `400` for DB-rejected values on CRUD/association writes, `503` for recognized temporary connection/capacity/lock failures, and `500` for unknown/internal failures. Reads use `500`/`503`. The generated file count remains seven fixed files plus three per entity; a shared compiler helper emits the classifier only into controllers around trusted generated model/database operations without adding runtime files or dependencies. The generic global Express fallback preserves safe malformed-JSON 400; every other error logs its stack and returns 500 with `Internal Server Error`, regardless of code/errno, because it has no database provenance. The envelope remains `{ success: false, error }`, without driver codes or SQL details. See `docs/generated-db-error-taxonomy-verification.md` for exact identifiers and operation statuses.
- Generated writes require JSON objects and reject unknown own keys, implicit id and synthetic FK columns. Trusted declared-field metadata validates type, REQUIRED presence/null and inclusive bounds/Unicode lengths before model calls; sanitized forwarding uses a fresh object. POST requiredness exempts DEFAULT and auto-generated keys, PUT stays partial, optional null is accepted and defaults stay database-applied. INT requires a finite safe integer, FLOAT finite number, BOOLEAN boolean, STRING string, ENUM exact member string. SQL is unchanged; OpenAPI reflects POST requiredness and rejects additional properties using operation-specific Create/Update/Read schemas. POST/PUT DB errors use the G06 taxonomy without uniqueness prechecks; generated malformed JSON is sanitized 400. Item GET, DELETE and relationship success/absence behavior is unchanged; caught DB errors use G06.
- Per-entity routers expose `GET /`, `GET /:id`, `POST /`, `PUT /:id`, and `DELETE /:id`.
- The generated server mounts routers directly at lowercase plural paths such as `/students`, without an `/api` prefix, and exposes `/health`.
- Relationship model/controller/routes are generated on the source entity. `MANY_TO_MANY` supports list/add/remove; `ONE_TO_MANY` supports list; `MANY_TO_ONE` and `ONE_TO_ONE` support singular lookup.
- ENUM POST/PUT checks enforce exact string membership before model calls. Optional
  null is allowed; supplied REQUIRED null is rejected. POST REQUIRED omission needs DEFAULT; PUT omission retains stored values. OpenAPI uses string + enum + default.
  The offline ENUM tests execute real emitted routers with mocked model methods;
  the opt-in MySQL harness also verifies native ENUM values, defaults and rejection.

## Collection GET contract

Only entity collection GET gains query support. Its body remains
`{ success: true, data: [...] }` with or without pagination. Item GET,
POST/PUT/DELETE, relationship methods/routes, and their response shapes are unchanged.

- Filters use exact SQL equality joined with AND in entity declaration order.
  Implicit `id` is exposed as INT through target-only metadata, without changing IR.
  Explicit STRING primary keys retain STRING parsing and ordering.
- INT requires a signed digit representation and a safe integer; FLOAT requires a
  finite decimal/exponent representation; BOOLEAN accepts exactly `true`/`false`;
  STRING retains raw text; ENUM requires exact declared membership, including an
  empty string only when declared. No special NULL filtering exists. STRING equality
  follows the existing SQL column collation. Write bounds are not reapplied to filters.
- `sort` accepts a known field. `order` accepts lowercase `asc`/`desc`, defaults
  to `asc`, and requires sort. Pagination without sort uses primary key ASC;
  non-primary sorting with pagination adds primary key ASC as a tie-breaker.
- `page` or `limit` enables SQL pagination with defaults 1/20 and maximum limit
  100. Both require positive decimal integers without leading zeros. Page, limit,
  and `(page - 1) * limit` must be safe integers. Without either parameter,
  collection behavior remains unbounded, with no automatic ordering or COUNT query.
- Paginated results include `X-Total-Count`, `X-Page`, `X-Limit`, `X-Total-Pages`.
  `COUNT(*)` reuses identical filters/parameters. Zero matches yields zero total
  pages; requests beyond the last page return empty data. Data and count are separate
  SQL reads, so concurrent writes can change the count between reads.
- `page`, `limit`, `sort`, `order` are reserved. Fields with those names can sort
  but cannot filter. Unknown parameters and repeated/non-string values return 400,
  as do invalid typed values, sort/order, pagination, and overflow. Validation occurs
  before any DB call, using the existing `{ success: false, error }` style.
  Collection DB errors use G06 sanitized 500/503 messages. A private model-owned
  WeakMap records safe query validation messages; the controller checks it only
  around parseQuery, before database access. Arbitrary statusCode/marker properties
  and registered errors thrown later by DB/model operations do not expose text.
- The controller invokes the model's `parseQuery` once and passes typed options.
  Model-owned `QUERY_FIELDS` metadata supplies trusted SQL columns; filter values,
  LIMIT, and OFFSET use mysql2 `pool.query` placeholders. Fixed ASC/DESC strings
  supply ordering. Data/count share `filterQuery`; no dependency is added.

## OpenAPI collection documentation

Collection GET includes optional page/limit/sort/order and non-reserved field filter
parameters, implicit id, proper scalar types and ENUM members, sort field enum,
lowercase order enum, pagination defaults/bounds, conditional metadata headers,
and 400 responses. Empty STRING and declared empty ENUM values set allowEmptyValue.
The existing component schemas and other operations are unchanged.

`swagger.json` uses OpenAPI 3.0.0. It describes CRUD and generated relationship paths without an `/api` prefix, maps DSL field types to JSON Schema types, marks `REQUIRED` fields, and includes numeric minimum/maximum, STRING minLength/maxLength, and default metadata. The generated server does not currently serve Swagger UI or the JSON file.

Path parameter schemas derive from the owning entity's primary-key datatype. Entities without an explicit primary key use the generated integer `id` column.
Operations use Entity.Create/Update/Read plus envelope components. Update omits PKs; optional fields are nullable. Synthetic FK columns remain exposed as readOnly. CreateResult models echoed fields without arbitrary default reload. Declared BOOLEAN rows normalize to true/false on source and target reads. General item/delete/relationship DB errors are sanitized.

## Download packaging

The web playground receives `generatedFiles` from `POST /api/compile` and builds `apiforge-project.zip` entirely in the browser. `frontend/app.js` writes a basic uncompressed ZIP whose entries are exactly the returned paths and contents. It does not package the repository's `output/` directory or APIForge development files.

If ZIP construction throws, the browser downloads a single `apiforge-generated-project.txt` concatenation instead. There is no server-side archive endpoint. Offline warning and collection tests execute the frontend ZIP writer and compare its entry names and contents to the current generation result.

## Standalone verification boundary

The opt-in `npm run test:generated-integration` harness verifies the generated project as a consumer artifact without mutating repository `output/`: it compiles representative DSL, materializes the in-memory files in a temporary directory, installs declared dependencies, starts the backend through `npm start` on an ephemeral port, confirms `GET /health`, stops the process tree, and removes the temporary project. It is intentionally excluded from the offline-friendly `npm test` command. The absence of a generated lockfile means compatible dependency releases may vary between integration runs.

This harness proves generated-project install and server startup, not database behavior. A complete DB-backed standalone claim still requires configuring MySQL, importing `database/schema.sql`, and exercising CRUD, validation, constraints, and relationships against that database.

## G22 internal planning contract

Complete generation uses one Effective Schema Plan after optimized IR. It owns
logical identity/fields, `roles.http`, separate trusted-model `modelPolicy`,
relationship storage and allocated resource/file/helper/path names. The
MySQL adapter owns physical representation/admission and SQL rendering;
OpenAPI and Express renderers consume the normalized facts. Exported partial
helpers remain tolerant and byte-compatible. Implicit identity and synthetic
FKs remain unknown HTTP inputs but trusted direct-create fields; every direct
update own identity property stays immutable before SQL, while FK payloads
remain trusted. Declared UUID/temporal checks are not broadened to synthetic
fields. Model.fields remains declaration-only with existing metadata shape.
See `docs/effective-schema-plan.md` and its verification report for ordering,
provenance, exact-output and guarded live-MySQL evidence.
