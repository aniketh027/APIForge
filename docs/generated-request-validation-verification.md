## Audit before implementation

The audit examined generated validation/controllers, model writes, source/effective
key metadata, defaults/constraints, physical relationship DDL, JSON middleware,
CRUD errors, OpenAPI, collection parsing and existing tests. An in-memory baseline
probe executed emitted validators and an actual emitted Express server before edits.
It accepted missing REQUIRED, numeric strings, fractional INT, numeric arrays,
unbounded STRING numbers, BOOLEAN numbers, fractional explicit INT PK, REQUIRED
INT null, unknown fields and array bodies. Malformed JSON returned HTTP 500 with
the generated global handler's generic error. These are baseline observations,
not conclusions inferred only from saved PASS values.

Answers to the requested contract audit:

1. POST and PUT both called the same exported `validate<Entity>(data)` function.
   It validated supplied ENUM membership, numeric comparisons and bounded STRING
   type/length; it did not distinguish create from partial update.
2. Both controllers passed the original req.body directly to model.create/update.
3. All request keys reached mysql2 object assignment, including implicit id and
   physically added relationship FK columns. Model.fields itself stayed declared-only.
4. Checks used value `!== undefined` and generally skipped null; omitted fields
   were unchecked. REQUIRED ENUM was the only special null rejection.
5. Defaults are typed `{ type, value }` field metadata, absent as null/undefined.
   SQL applies DEFAULT; controllers neither inject defaults nor reread create rows.
6. Effective-key metadata marks implicit id and explicit INT PK without DEFAULT
   as autoGenerated. Explicit STRING PK and INT PK with DEFAULT are not auto-generated.
7. Strict Express JSON parsing forwarded entity.parse.failed to a generated
   global handler that always returned 500; reproduced over HTTP.
8. POST/PUT returned arbitrary model error.message, including duplicate-entry
   values/index names and other driver/SQL details.
9. Declared field/type/constraint/default/validation metadata and getEffectiveKey
   are sufficient. Body validation need not use collection parser logic, whose
   filters intentionally convert HTTP strings to typed values.
10. Old STRING-length tests accepted REQUIRED null; the guide verifier accepted
    REQUIRED BOOLEAN null, numeric strings and fractional INT. A main-suite
    omission test used an undeclared name that was silently ignored. Historical
    fixtures protected old controller/model/server/OpenAPI bytes. These assertions
    were narrowly updated or projected only for the approved changed sections;
    historical fixture files were not recaptured.

## Final runtime contract

POST/PUT require JSON objects. Shape is checked first, then unknown own keys in
received Object.keys order, then fields in declaration order. Each field checks
POST required omission, REQUIRED null, type, then inclusive MIN/MAX/length bounds
or exact ENUM membership. Only the first error returns, with HTTP 400 and
`{ success: false, error: <deterministic message> }`.

The shared validator now accepts an operation, defaulting to update for existing
direct-validator callers. POST explicitly passes create; PUT uses partial mode.
Trusted WRITE_FIELDS is emitted solely from declared fields. RequiredOnCreate uses
REQUIRED AND no DEFAULT AND not autoGenerated effective key. Omission is an own-
property test, distinct from explicit null or an invalid supplied undefined value.

| Value/policy | Result |
|---|---|
| POST missing REQUIRED without DEFAULT/generated key | 400 before model |
| POST missing REQUIRED with DEFAULT or auto-increment PK | Allowed; database supplies value |
| PUT omitted field, including REQUIRED; PUT {} | Allowed; current stored value retained |
| REQUIRED null, any datatype | 400 before model |
| Optional null, any datatype including ENUM | Allowed; non-null checks skipped |
| INT non-null | typeof number, finite, safe integer, then inclusive MIN/MAX |
| FLOAT non-null | typeof number, finite, then inclusive MIN/MAX; integer numbers allowed |
| BOOLEAN non-null | typeof boolean |
| STRING non-null | typeof string, even unbounded; Array.from(value).length bounds |
| ENUM non-null | Exact case-sensitive member string, declaration order retained |
| Unknown, implicit id, synthetic relationship FK own property | 400 before model |
| Declared explicit INT/STRING PK | Recognized and validated on POST/PUT |

No defaults are injected, uniqueness prequeries or duplicate-key detection added,
or duplicate JSON-key detection invented. MIN/MAX are inclusive. INT safe-integer
validation intentionally does not enforce MySQL's physical INT32 range. FLOAT
capacity/precision and other physical target rules remain separate.

After validation, controllers build a NEW object by iterating trusted declared
fields and copying only supplied own properties. Object.defineProperty creates
own data properties safely even for prototype-sensitive names; inherited request
properties cannot authorize fields. No raw req.body reaches create/update.
Implicit id remains outside AST/symbols/IR/Model.fields and is returned from
insertId. Source-declared PK acceptance, including PUT mutation, remains compatible.

Empty valid POST uses `INSERT INTO <table> () VALUES ()` so MySQL can supply keys,
defaults and nullable values; the previous empty mysql2 SET object cannot form a
valid insert. Nonempty create still uses bound SET ?. Empty PUT still rereads via
findById. Create responses retain their existing assembly and do not reload defaults.

Generated entity.parse.failed now returns sanitized HTTP 400 with
`Request body must contain valid JSON.` Strict Express parsing remains unchanged:
valid scalar JSON is also rejected with sanitized 400 before the controller;
arrays reach its object-shape check. POST/PUT model errors return sanitized 500
`Unable to create item.` / `Unable to update item.` regardless of driver message
or driver statusCode. Compiler `/api/compile` malformed JSON remains 500/INP002,
verified against its actual server.

## Scope and remaining gaps

G03 and G04 are fixed. G05 body shape and unknown/generated-field authority are
fixed within this milestone's declared-field policy. G06 is repaired only for
metadata-known input validation, generated POST/PUT error sanitization and generated
JSON parse errors. Item GET, DELETE and relationship error behavior remains unchanged;
their raw DB messages and broader error/status unification remain separate.

G12 explicit-key create/default response semantics remain unchanged (e.g. a
database-supplied default key is not reread, and missing non-REQUIRED STRING PK
remains a database concern). G13 remains open: explicit declared PK writes are
accepted, and a key-changing PUT may reread the old path key. No mutation redesign
or physical numeric policy was introduced.

OpenAPI minimally reflects POST required omission exemptions and
additionalProperties: false. Default/type/bounds/ENUM metadata is preserved; implicit
id remains integer/readOnly and not required input. PUT still reuses POST's schema,
and optional null/full response modeling remains incomplete. These G11 limitations
are documented, not claimed fixed. G07-G28 were not silently folded into this work.
