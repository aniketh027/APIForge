## Physical planning and indexes

`physicalPlan` retains original nodes for diagnostics, with physical columns,
origin, type, nullability, index kind and ordered key parts. All entity tables
are planned before relations, matching SQL emission. An explicit key uses its
declared column; otherwise the plan prepends INT id. A relationship adds its
column to the actual receiver. Junctions copy both effective-key physical types.
AST, symbols, IR and optimizer contents remain unchanged.

An FK requires an index whose ordered leftmost prefix matches its columns.
ONE_TO_ONE first adds UNIQUE, which supports its FK without a second index.
M2M PRIMARY(source_fk,target_fk) supports the source FK and needs only one
additional target FK index. A declared PRIMARY KEY UNIQUE really produces two
indexes on stock MySQL; the plan counts both. Native information_schema checks
compare every accepted plan's column count, index count, primary key parts,
actual engine and row format with imported tables.

The requested 64-secondary boundary required correction based on native
evidence: 63 UNIQUE/FK/mixed/ONE_TO_ONE secondary indexes plus PRIMARY imported;
64 plus PRIMARY failed ER_TOO_MANY_KEYS/1069. The independent InnoDB
64-secondary guard remains, alongside the stock SQL-layer 64-total guard.
The compiler does not pretend to inspect a custom server's build-time index cap.

Key widths exclude row length/null metadata: STRING is generated capacity x4;
UUID is 36 ASCII bytes; INT/FLOAT/TIMESTAMP are 4, DATE 3, BOOLEAN 1 and ENUM
1/2. Native M2M boundaries passed STRING(759)+UUID=3072,
STRING(767)+INT=3072, and UUID+UUID=72. The next STRING character failed
ER_TOO_LONG_KEY. Existing individual STRING and STRING+STRING tests remain.

Current PRIMARY keys have <=2 parts and <=3072 bytes. Secondary leaf records
append missing primary columns, so their maximum data contribution is <=6144
bytes plus small headers/length/null metadata, below the local record envelope.
Their node-pointer records also fit. No extra source restriction is needed for
these currently generated index records.

## Row budgets

| Physical type | Maximum payload bytes |
|---|---:|
| INT | 4 |
| FLOAT | 4 |
| BOOLEAN / TINYINT | 1 |
| DATE | 3 |
| TIMESTAMP, no fractional seconds | 4 |
| UUID CHAR(36) ascii | 36 |
| ENUM <=255 / >255 members | 1 / 2 |
| STRING VARCHAR(N), utf8mb4 | 4N |

The logical budget sums all physical payloads, VARCHAR one/two-byte length
prefixes and ceil(nullable columns /8). APIForge's minimum STRING capacity is
255 characters, so its utf8mb4 VARCHAR prefix is two bytes. Primary/junction keys
are nonnullable; synthetic relationship columns are nullable. InnoDB MVCC/header
bytes belong to the separate local budget. Fixed-only tables cannot approach the
logical limit within the physical column/local limits; relevant wide VARCHAR
tables use the packed SQL row representation.

Native boundaries: implicit INT id + nullable VARCHAR(16382) =65535 accepted;
VARCHAR(16383) with that id requires 65539 and failed. Two individually-valid
VARCHAR(9000) columns failed. VARCHAR(8190)+VARCHAR(8191)+two BOOLEAN columns,
implicit id and bitmap also reached 65535 and imported. Synthetic UUID FKs
contribute their full 36-byte payload and null metadata.

The local estimator follows the inspected 8.4 admission code rather than
guessing how individual runtime records spill. It budgets 5 header bytes, the
6-byte transaction ID, 7-byte roll pointer, nullable bitmap, fixed payloads, and
a one-byte row-version allowance on receiver tables changed by ADD COLUMN.
Long DYNAMIC variable fields use the worst unexternalized 40-byte payload plus
one length byte. The external 20-byte reference plus two length bytes is smaller.
This avoids both summing all VARCHAR maxima locally and assuming every long
field can always be represented by a 20-byte pointer alone.

MySQL's inspected 16 KiB admission threshold rejects record sizes >=8126; the
supported budget is therefore <=8125. Native tests imported 224 nullable UUIDs,
rejected 225, and imported 224 UUIDs +9 BOOLEANs (8125), while +10 BOOLEANs
(8126) failed. Fixed + VARCHAR and synthetic UUID FK overflow cases also failed.
60 default VARCHAR columns imported through DYNAMIC off-page behavior. Truly
short SQL VARCHAR columns are not generated: STRING capacity is always >=255.

This is a conservative schema admission envelope, not an exact row-layout or
runtime spill simulator. The 16 KiB floor can reject schemas that would fit
larger pages. The row-version allowance can conservatively reject a borderline
schema that a rebuilding ALTER would accept. Runtime values, later migrations,
custom MySQL builds and resource/configuration failures remain DB-authoritative.
The live local-record rejection witnesses specifically use 16 KiB pages.

## ENUM, names, literals and diagnostics

ENUM count violations locate the field's datatype. Member length/byte violations
locate the actual member occurrence, including later members. Existing duplicate,
trailing ASCII-space, exact membership, DEFAULT and utf8mb4_bin rules are retained.
Source and forged-IR tests cover 65535/65536 members, a 255-astral-character
1020-byte member, 256 ASCII characters, and 256 astral characters/1024 bytes.

Internal name checks run on the final plan, including the synthetic db_ROW_ID
produced by entity Db with key ROW_ID. They are target rules, not lexer reserved
words. Numeric DEFAULT checks address demonstrated ER_INVALID_DEFAULT failures
only: INT [-2147483648,2147483647], FLOAT absolute maximum
3.4028234663852886e38. A slightly larger FLOAT that still rounds to a finite
Math.fround value also fails native DDL and is rejected. Large legal MIN/MAX
CHECK literals and HTTP/runtime numeric behavior are unchanged.

All new semantic failures reuse SEM037 / MYSQL_TARGET_LIMIT; no registry entry
is added. Column/index errors locate the contributing field or relationship
that crosses the limit. Row failures locate the owning table/entity. Messages
provide the generated object, computed quantity, limit and corrective direction.
The analyzer passes the member occurrence to the existing location resolver.
Existing identifier, single-column, key, AUTO_INCREMENT and G17 diagnostic
behavior is preserved; redundant single-VARCHAR table errors are suppressed.

Semantic failures precede IR lowering. `Codegen.generate` independently validates
forged IR and runs the same physical preflight before content generation or disk
publication. Negative tests start with existing output/schema.sql and a user
.env, then verify unchanged bytes and no staging/publication artifacts for every
new invalid fixture. The live oracle intentionally invokes the raw SQL emitter
for rejected source to obtain an independent native rejection witness; this does
not replace the production generation gate. G19 implementation is unchanged.
