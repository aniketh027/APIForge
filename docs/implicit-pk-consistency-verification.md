## Design and observed correction

The private `getEffectiveKey(entity)` in src/codegen/codegen.js is the single
code-generation key authority. It returns declared key metadata plus origin
explicit and the current MySQL auto-generation policy, or id/INT/origin implicit/
autoGenerated true. Explicit INT with DEFAULT still omits AUTO_INCREMENT.
SQL, model predicates/create identity, source/target relationship helpers,
collection field metadata/default ordering/tie-breaking, and OpenAPI key types
consume that authority. Controllers pass the existing URL :id through to models;
they do not independently resolve keys.

For `ENTITY Student` with `name STRING` and `age INT`, old emitted model queries
used WHERE name = ? for findById, update, update reread and delete. Old create
returned `{ name: result.insertId, ...data }`, losing the ID when name was supplied.
SQL and collection queries already used the generated integer id. Source relation
helpers could use parent_name while SQL allocated parent_id.

Corrected item queries all use WHERE id = ?. Create returns
`{ ...data, id: result.insertId }`: insertId 42 yields id 42 while name/age remain
intact. All four source relation cardinalities use the same effective key as DDL.
SQL for ordinary implicit entities stays byte-identical. Routes, pluralization,
:id spelling, response envelopes/statuses and partial PUT behavior are preserved.

AST declarations, semantic field symbols, source ADD_FIELD instructions and
optimized IR retain only declared fields. Generated Model.fields also remains
declared-only. Collection query/read metadata includes implicit id. OpenAPI adds
`id: { type: integer, readOnly: true }` to the existing component, without adding
id to required. This is the smallest compatible change to reused components;
it does not introduce a new schema hierarchy or request filtering.

Caller-supplied implicit id remains forwarded under existing write behavior.
A stubbed DB test proves insertId cannot be hidden by the response object spread,
but does not establish live MySQL AUTO_INCREMENT semantics for submitted ids.
Ordinary supported POST tests omit id. G05, G12 and G13 remain separate.

## SEM033 and warnings

SEM033 is the only new public assignment; symbol IMPLICIT_PRIMARY_KEY_COLLISION,
phase semantic, severity error. An entity with no explicit PRIMARY KEY and an
ordinary id/Id/ID/iD field is rejected because the MySQL column allocation would
collide. It neither promotes nor renames a field. The message names both the
entity and conflicting spelling; the hint is exactly:

> Declare an explicit PRIMARY KEY or rename the conflicting field.

Parsed sources locate the field name with the existing exclusive end range.
The tested indented two-character name spans line 2, columns 3 through exclusive
5; multiline declarations also locate the name correctly. Explicit id or ID
STRING keys, and ordinary id-like fields alongside another explicit key, remain
valid. Semantic failure skips IR/optimizer/codegen, returns HTTP 422, CLI exit 1,
and no generated files. No WRN001 is emitted for the invalid collision program.

All original 61 public errors remain mapped exactly as at baseline; total errors
are now 62. WRN001–WRN005 retain their assignments and behavior. Normal implicit
entities retain WRN001's complete wording, hint, severity and entity-name location.
