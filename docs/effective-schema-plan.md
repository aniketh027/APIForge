# Effective Schema Plan

G22 introduces an internal normalization boundary after optimized IR and within
the existing code generation phase. The compiler still has six public phases.
AST, symbols, IR, optimized IR, compiler API responses and CLI JSON retain their
source-declared shapes. Synthetic identity and relationship fields exist only in
the internal plan and generated artifacts.

`src/planning/effective-policy.js` owns shared, pure identity and service policy.
`src/planning/effective-schema.js` builds the normalized plan and a separate
provenance sidecar. Full `generate()` builds one candidate, preserves the existing
preflight order, verifies structural coherence, and passes its plan to renderers.
Semantic analysis uses tolerant policy/projection helpers; it does not call the
strict post-IR entry point.

## Canonical data

The versioned plan contains ordered entities and relationships. Entity records
contain source spelling, allocated logical names, one effective field array,
`key: { fieldId, generation }`, and `modelPolicy`. Fields contain stable IDs,
logical name/type, typed default, constraints, ordered validations, origin,
storage facts and `roles.http`. Relationships contain `relationName`, endpoint
IDs, cardinality, logical names and normalized storage.

IDs encode scoped name tuples with escaped components: entity spelling; entity
plus declared field spelling; entity plus implicit key; or relationship scope
plus endpoint/field spelling. They do not depend on lines, traversal ordinals,
object identity, content hashes, or MySQL names. Declaration and relationship
order remain observable presentation order. IDs remain stable when unrelated
declarations or source positions change.

The plan is JSON data: no AST/IR pointers, functions, Maps, Sets or cycles.
Prototype-sensitive spellings are ordinary values. Numeric preflight runs on
the original primitive values before structural admission. The canonical data
never acquires MySQL capacities, encodings, index limits or DDL fragments.

## Identity

| Canonical generation | Meaning | Legacy key helper |
|---|---|---|
| `database_integer` | Database generates an integer identity | `auto_increment` |
| `runtime_uuid` | Application generates an omitted UUID identity | `runtime_uuid` |
| `none` | Supplied/defaulted/database-authoritative identity | `none` |

An absent declared key produces an `implicit_key` INT field named `id`.
Declared INT and UUID keys without defaults select their corresponding generation
intent. Typed defaults, including zero, false and empty strings, retain their
original values. Only a selected identity gets generation intent.

`getEffectiveKey()` is a compatibility wrapper. Its legacy object preserves
declared field properties and property presence, uses `origin: explicit|implicit`,
maps `database_integer` to `auto_increment`, and reports `autoGenerated` for both
generated modes. This compatibility vocabulary is not canonical plan vocabulary.

## HTTP roles and direct model policy

Each field has `roles.http.create`, `update`, `read`, `createResult` and
`collection`. These facts describe generated HTTP behavior, including acceptance,
requiredness, nullability, exposure, immutability and collection candidacy.

| Field category | HTTP POST | HTTP PUT | Direct model create | Direct model update |
|---|---|---|---|---|
| Ordinary declared | Accepted and validated | Accepted and validated | Trusted; declared UUID/temporal checks | Trusted; declared UUID/temporal checks |
| Explicit identity | Accepted; generation/default permits omission | Immutable own property | Trusted; identity resolution | Immutable own property before SQL |
| Implicit identity | Unknown field | Unknown field | Trusted payload | Immutable own property before SQL |
| Synthetic FK | Unknown field | Unknown field | Trusted payload | Trusted payload |

The model contract is explicit:

```json
{
  "createPayload": "trusted",
  "updatePayload": "trusted_except_identity",
  "identityUpdate": "immutable",
  "writeValidation": "declared_uuid_temporal"
}
```

It does not apply HTTP whitelisting or ordinary scalar validation to direct
model calls. UUID and temporal validation continues to cover declared fields
only. SQL remains authoritative for trusted relationship writes and ordinary
model values. Collection candidates include implicit identity and declared fields;
synthetic FKs are excluded. Reserved `page`, `limit`, `sort`, `order` fields are
sort candidates but cannot be HTTP equality filters.

Views preserve the established output order: base SQL/query/base Entity puts an
implicit key first; Create/Update and `Model.fields` use declaration order; Read
uses declared fields, implicit identity, then FKs in relationship order;
CreateResult uses declared fields then implicit identity. Junction columns use
source then target order. View selectors reference the one field array.

## Relationship storage

| Cardinality | Storage | Nullable | Unique | Delete action |
|---|---|---|---|---|
| ONE_TO_MANY | Source-key FK on target | Yes | No | SET NULL |
| MANY_TO_ONE | Target-key FK on source | Yes | No | SET NULL |
| ONE_TO_ONE | Source-key FK on target | Yes | Yes | CASCADE |
| MANY_TO_MANY | Source/target FKs in a junction | No | Composite primary key | CASCADE on both |

Receiver/reference decisions and junction topology are normalized once. An FK
copies the referenced key's logical type, not its default, PK/REQUIRED flags,
generation or validations. `typeSourceFieldId` identifies the referenced field
whose physical STRING width a target adapter must use. Junction fields remain
inside relation storage and never become entity model/HTTP fields.

## Names and provenance

`target-names.js` supplies the existing pure lower-first and pluralization
transforms, entity/relation name projection and namespace reservation. The
planner uses those exact projections for resource paths, file paths, bindings,
CRUD/relationship helpers, parameters, segments, FKs and junctions. There is no
second transform or suffix allocator. MySQL CHECK and FK constraint names belong
to the MySQL naming profile, outside canonical logical names.

The provenance sidecar is keyed by stable IDs. It copies available primitive
locations and contributor IDs, without AST/IR pointers. Missing IR spans remain
missing. Wrapper-local source contexts preserve original diagnostic node
identity where legacy semantic callers require it. Ordered contributor arrays
retain duplicate declarations during tolerant preflight; reference lookup
retains its historical last-entity/first-key behavior. These contexts are outside
the canonical plan and provenance. Primitive legacy field extras are retained
there for exact `Model.fields`, `WRITE_FIELDS` and `PRIMARY_KEY` presentation.
Source lines never appear in canonical data.

## Target adapters and future work

The MySQL adapter consumes effective columns, identities and relation storage.
It owns SQL types/quoting/literals, VARCHAR widths, UUID CHAR encoding,
AUTO_INCREMENT mapping, physical index/check/FK names, support-index reuse and
G16 row/key/column/index/ENUM/default admission calculations. SQL rendering and
preflight use the same logical facts. OpenAPI owns presentation types, formats,
descriptions, envelopes and status responses; field roles and relation topology
come from the plan. Non-UUID association URL echoes remain strings.

For G26 the intended flow is Effective Schema Plan to MySQL Physical Snapshot.
A later snapshot must include physical column types/defaults/generation, ordered
PKs, unique/support indexes, CHECKs, FK references/actions and physical names.
G22 provides the stable logical references and transient MySQL adapter data;
snapshot persistence, comparison and migration execution are outside this task.

For G27 the shared plan supplies logical entities/effective fields, integer
generation intent, defaults, HTTP roles, model policy, relation topology and
logical names. A PostgreSQL adapter must supply its types/quoting/generated
integer DDL, identity retrieval, enum strategy, constraints/indexes, target
limits, runtime driver and query generation. G22 adds no PostgreSQL runtime.

## Compatibility and admission

Existing extraction, key, SQL/model/controller/route/server/Swagger/OpenAPI,
MySQL planning and transform exports retain their signatures. Standalone helpers
project incomplete legacy definitions tolerantly; they do not run full production
preflight. Full generation admits empty PROGRAM, ADD_FIELD-introduced entities,
collapsed repeated CREATE_ENTITY and established representable forged IR.

Complete generation preserves failure precedence: IR validation, existing
MySQL/numeric/ENUM checks, existing naming checks, existing endpoint checks,
then new structural checks. Narrow newly rejected contradictions are duplicate
effective/storage names, implicit-key collision and competing declared keys;
unresolved endpoints retain their earlier errors. This is not semantic
revalidation of arbitrary direct IR.

Closure requires no independent downstream derivation of effective identity,
generation, synthetic FKs, receiver/junction topology, HTTP roles or allocated
logical names. Delegating compatibility wrappers and target presentation remain
allowed. Exact ordered generated file arrays are compared against the complete
compiler dependency closure at `d91859e30a5ed0f91be9826a3d8d3a5c5b7261ce`;
no output or line-ending normalization is permitted.
