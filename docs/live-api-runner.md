# Local Live API Runner

Live API runs one disposable generated backend for a local development/professor demonstration. It is disabled by default. Set `APIFORGE_LIVE_RUNNER=1` on the APIForge dev server and configure the selected database target explicitly:

| MySQL | PostgreSQL |
| --- | --- |
| `APIFORGE_LIVE_MYSQL_HOST` | `APIFORGE_LIVE_PG_HOST` |
| `APIFORGE_LIVE_MYSQL_PORT` | `APIFORGE_LIVE_PG_PORT` |
| `APIFORGE_LIVE_MYSQL_USER` | `APIFORGE_LIVE_PG_USER` |
| `APIFORGE_LIVE_MYSQL_PASSWORD` | `APIFORGE_LIVE_PG_PASSWORD` |

All four variables are required; an explicitly empty password is allowed for local test accounts. There is no fallback to `DB_*`, `PGPASSWORD`, password files, browser tokens or generated `.env` files. PostgreSQL administration uses `APIFORGE_LIVE_PG_ADMIN_DB`, defaulting to `postgres`. Both administration and import connections resolve the exact dedicated password through a callback, including an empty string. Host, port, user and database are explicit; TLS is disabled for this local demo contract, encoding is UTF8, replication is disabled, and startup options/timeouts and application name are fixed independently of ambient pg settings. The optional `NODE_PG_FORCE_NATIVE` driver is refused before SQL because its libpq environment/service contract is unsupported. Use local demo administration accounts with permission to create/drop databases. Existing MySQL 8.4 and PostgreSQL 18 compatibility requirements apply.

Compile successfully, open **Live API**, and explicitly press **Start live API**. Select a generated OpenAPI operation, fill its path parameters, optionally add a query component and JSON body, and send. Generated error HTTP statuses remain visible responses. Press **Stop live API** to destroy the runtime. Changing source/target, loading an example/demo, clearing, compiling again, or leaving the page attempts to stop it. Server ownership and the absolute 15-minute lifetime provide cleanup independently of the page.

The server accepts only source and target at start, rejects IMPORT just like the browser compiler, and runs all real phases in memory. It writes identical generated bytes inside a fresh OS temp directory, imports only the compiler schema into a random `apiforge_live_` database, and launches the exact generated server using Node and a trusted loopback-only listener preload. `NODE_PATH` uses APIForge's installed dependencies. No session-time npm install, temp node_modules, or secret .env file is needed. Credentials are child environment values and never browser data. Live routes require explicit opt-in, a loopback socket peer, an explicit localhost/loopback Host header, and a same-origin browser request when Origin is present. Host validation blocks DNS-rebinding hostnames; X-Forwarded-Host, Forwarded and X-Forwarded-For confer no access.

One runtime exists per dev-server process. Start/stop/request transitions serialize. New starts destroy the previous runtime first. Opaque tokens authorize requests/stops; status exposes no token, port, path, PID, database name or credential. Forwarding is fixed to the owned loopback process and allowlisted generated methods/path templates, with one safe segment per parameter. Encoded separators, nested percent encodings, dot traversal, fragments and URLs are rejected. JSON bodies are limited to 64 KiB, responses to 1 MiB, and requests to 10 seconds. Only content-type and pagination headers are returned. Child output is bounded and stays internal; public errors use fixed messages.

Cleanup attempts process-tree termination, port release, closing administration/import connections and directory removal even when an earlier step fails. Database deletion requires these process/port/connection prerequisites to succeed and a positively acknowledged CREATE for the exact random Live name. Generated pools close with the process. A later schema-import failure still permits cleanup of the acknowledged, owned database. A failed DROP retains confirmed ownership for retry of the same resource; an acknowledged DROP is never repeated, even if closing its administration connection subsequently fails.

A known duplicate-name refusal never adopts or deletes the existing database. After connections and temporary resources are cleaned up, a new Start can proceed with a fresh random name. If CREATE acknowledgment is lost, times out, or otherwise fails without an explicit duplicate refusal, the outcome remains uncertain. No DROP or CREATE retry is issued for that resource. The manager retains private pending cleanup and blocks every replacement Start and shutdown cleanup attempt with the existing sanitized `LIVE_CLEANUP_FAILED` response. Random names and general connection-error codes do not prove ownership.

For confirmed-owned cleanup failures, retry Stop while retaining the token, or allow local shutdown cleanup to retry after restoring the failed prerequisite. An uncertain start has no session token to recover through Stop. Operators must suspend new Live use and independently assess the failed operation using trusted server-side evidence and database administration records. Establish ownership and the actual CREATE outcome before taking manual action against any exact resource; never reset or delete databases by prefix alone. Restarting the dev server loses its in-memory uncertainty record and must not be used to bypass that assessment. There is no automatic recovery or destructive repair endpoint. SIGINT/SIGTERM handlers are installed only when `server.js` is the executable entry point. Repeated Stop after success returns `LIVE_SESSION_INVALID`.

Run `npm run test:live-api-runner` for offline equivalence, lifecycle, security and transport checks; run `npm run test:frontend-live-api` for browser tests. Run `npm run test:live-api-runner-native` for the real Professor Demo User CRUD lifecycle on **both** targets. The native test may map existing `APIFORGE_TEST_DB_*` MySQL configuration or `APIFORGE_TEST_PG_*` PostgreSQL configuration into an isolated test manager, or use the existing disposable PostgreSQL Docker helper. Production does not use these fallbacks. Missing native infrastructure exits nonzero and reports **NATIVE BLOCKED**; both complete lifecycles are required for **NATIVE COMPLETE**.

Limitations: local opt-in only, no production hosting, authentication, filesystem imports, remote proxy, streaming, uploads, browser-selected credentials or databases, or multi-session support. Hard termination/power loss cannot run JavaScript cleanup or preserve in-memory ownership/uncertainty state. Operators may need to assess retained databases/directories and remove resources only after independently verifying ownership. This feature does not change generated templates, compiler semantics, ordinary output publication, or the compiler API contract.
